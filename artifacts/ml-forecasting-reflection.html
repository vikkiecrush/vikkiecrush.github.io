ARTIFACT 05 Machine Learning Model Validation Forecasting

Reflection on a Machine Learning Project: Walmart Sales Forecasting

A model-validation retrospective on a published retail forecasting study I co-authored — revisiting eight competing ML models, an extremely high reported R², and the validation strategy I would rebuild from scratch with what I know now.

Field: Applied Machine Learning · Retail Forecasting · Course: AIML 500, Module 5.3 (Model Validation and Verification) · Format: Technical Reflection on a Published Study

Introduction

Most of the artifacts in this portfolio show me building something new. This one is different on purpose: it is a retrospective on a machine learning project I already finished — a peer-reviewed study forecasting Walmart weekly sales that was later published in the Asian Journal of Probability and Statistics (Neba et al., 2024), where I contributed as a co-author. Revisiting a completed, published project with fresh eyes is its own kind of skill. It is easy to defend work you already shipped; it is more useful — and more honest — to ask what a rigorous reviewer would ask a year later: would this model actually survive contact with production?

Description

This artifact compares eight machine learning models — from Linear Regression to XGBoost and LightGBM — trained on a public Kaggle Walmart sales dataset (2010–2012) to forecast weekly store sales. It reports the original results, audits the original methodology honestly (including a validation strategy I now believe was flawed), and lays out the specific, concrete changes I would make if I ran this project again today: a time-aware validation strategy, systematic hyperparameter tuning, and a post-deployment monitoring plan grounded in the NIST AI Risk Management Framework.

Objective

The original project's objective was to determine which machine learning model could most accurately forecast Walmart's weekly sales using historical sales, holiday indicators, temperature, fuel prices, Consumer Price Index (CPI), and unemployment — and to generate insights that could support inventory planning and other retail decisions. This reflection's objective is narrower and more critical: to evaluate whether “most accurate on a held-out test set” is the same thing as “ready for production,” and to specify exactly what would need to change if it were not.

The Original Data Preparation & Modeling Approach

We began with exploratory data analysis to understand variable distributions, correlations, and patterns. Outliers were addressed with Winsorization — capping extreme values rather than discarding observations — applied to weekly sales, holiday flag, temperature, fuel price, CPI, and unemployment. We then used random sampling to split the data into roughly 80% training and 20% testing, with a fixed random seed for reproducibility.

We compared eight models spanning a full range of complexity: Linear Regression, Multiple Regression, a Generalized Linear Model (GLM), Decision Tree, Random Forest, Gradient Boosting Machine (GBM), XGBoost, and LightGBM — specifically to test whether advanced ensemble methods could capture relationships that simpler linear models could not.

Model Performance Results

Model performance was evaluated with three complementary metrics: Mean Absolute Error (MAE), Root Mean Squared Error (RMSE), and R². XGBoost produced the strongest reported numbers by a wide margin over the linear baseline:

Model MAE RMSE R²
XGBoost (best) 1,226.471 1,700.981 ≈ 0.99999
Linear Regression (baseline) 35,632.510 80,153.858 —

Source: Neba et al. (2024), Asian Journal of Probability and Statistics, 26(7), 1–23.

Looking back, I understand more clearly why using multiple metrics matters here. MAE gives an intuitive, easily communicated average error size. RMSE penalizes large errors more heavily — important in retail, because a handful of very large forecasting misses can drive real stockouts or excess inventory that an average error hides. R² provides a third lens on model fit, but I would not use it alone: an R² of essentially 1.0 is exactly the kind of result that should trigger more scrutiny, not less, before I'd trust it on unseen future data.

Ethical Considerations

One genuine strength of the original project was that we looked beyond aggregate accuracy. The dataset had no demographic fields, so we used holiday vs. non-holiday period as a proxy subgroup split. Several of the advanced models had substantially lower error during non-holiday periods — evidence that strong overall performance does not guarantee equally reliable predictions under every condition, which is exactly the kind of hidden failure mode a fairness-blind evaluation would miss.

The study also discussed algorithmic bias, transparency, and accountability at a general level. In hindsight, I believe privacy deserved more direct treatment rather than being folded into that broader discussion. The dataset carried no personally identifiable customer information, which limited immediate risk — but if a future version incorporated customer-level purchasing or behavioral data, I would insist on data minimization, explicit access controls, and formal privacy governance before a single model was trained on it.

Improvements Based on What I Know Now

If I ran this project again today, two changes matter more than any tweak to model choice.

1

Replace the Random Split with Time-Aware Validation

We used a random 80/20 train-test split. For a forecasting problem, randomly mixing observations across time periods does not represent the real-world task, where historical data must predict a genuinely unseen future — and can let a model quietly train on information from “future” rows relative to what it is being tested on.

  • Use chronological train / validation / test periods, or rolling time-series cross-validation, instead of a random split.
  • Scikit-learn explicitly warns that standard cross-validation can be inappropriate for time-ordered data for this exact reason (Scikit-learn Developers, n.d.).
  • Reserve the most recent period as a completely untouched final test set, never seen during any tuning step.
2

Systematic Hyperparameter Tuning, Not Defaults

We relied primarily on default model settings. I would instead systematically tune parameters such as learning rate, tree depth, number of boosting rounds, and regularization — using the time-based validation split above, not the original random one — to build real evidence that XGBoost's near-perfect result generalizes, rather than reflects leakage from the split itself.

Post-Deployment Monitoring Plan

The original project was a research study, not a live deployment, so no monitoring system ever ran against it. If I deployed this model today, I would establish baseline MAE and RMSE values and compare every forecast cycle's predictions against actual sales — tracked separately for holiday and non-holiday periods, since that is exactly where the original analysis found performance gaps.

I would also monitor the input distributions themselves — CPI, unemployment, fuel prices, temperature, and holiday patterns — for data drift, with a full model review on a monthly or quarterly cadence. Consistent error deterioration, significant drift, or a major shift in consumer behavior would trigger investigation and, if warranted, retraining. This mirrors the NIST AI Risk Management Framework's emphasis on continuously measuring and managing AI risk across the full system lifecycle, not just at launch (NIST, 2023).

Process

I returned to the original study, its methodology, and its published results, and asked a reviewer's question of my own past work: which parts hold up, and which would not survive a rigorous model-validation audit? I traced the random train/test split forward to its actual consequence for a time-ordered forecasting problem, cross-checked the correct alternative against the scikit-learn documentation on time-series validation, and grounded the monitoring plan in the NIST AI RMF rather than inventing an ad hoc checklist. I used ChatGPT to help organize and tighten the wording of this reflection and to help surface areas of the original project worth revisiting — the analysis, the model audit, and every final judgment call are my own.
